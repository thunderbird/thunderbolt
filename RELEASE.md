# Release Guide

This guide explains how to create and publish releases for Thunderbolt using GitHub Actions.

## Overview

Our release process uses GitHub Actions to automate building and publishing releases for all platforms:

- **Desktop**: Linux, macOS (Intel + Apple Silicon), Windows (x64 + ARM64)
- **Mobile**: iOS (TestFlight), Android (Play Store Internal Track)
- **CLI**: `thunderbolt` binaries for `darwin-arm64`, `linux-x64` and `linux-arm64`, attached to the same `v{version}` GitHub Release

`release.yml` runs `version-bump.yml` first, then fans out to `desktop-release.yml`, `ios-release.yml`, `android-release.yml` and `cli-release.yml` in parallel. It has two entry points and no others: a `workflow_dispatch` (Actions UI or `gh workflow run`) and a nightly `schedule` (see [Nightly Releases](#nightly-releases)). No workflow in the repository has a tag trigger, so pushing a version tag by hand builds nothing.

## PR Title Convention

PR titles are validated by `.github/workflows/lint-pr-title.yml` and drive automated changelog generation (since the repo uses squash-merge, the PR title becomes the commit on `main`).

Two formats are accepted:

**Conventional Commits** (preferred):

```
<type>[(<scope>)]: <description>

feat(THU-58): add changelog automation
fix: remove invalid header on mobile
chore(deps): bump @tauri-apps/api to 2.11.0
```

Allowed types: `feat`, `fix`, `chore`, `docs`, `refactor`, `perf`, `test`, `ci`, `build`, `style`.

**Legacy `THU-XXX:` format** (accepted, prefer Conventional going forward):

```
THU-58: add changelog automation
```

Invalid titles (e.g. `random text`, missing type, missing description) fail the `Lint PR Title` check and block merge.

## Quick Start

The easiest way to create a release is via GitHub Actions:

```bash
# Via GitHub CLI (recommended)
# Release to ALL platforms (Desktop + iOS + Android + CLI)
gh workflow run release.yml -f version_type=auto  # Auto-detect from commits
gh workflow run release.yml -f version=1.2.3      # Explicit version
gh workflow run release.yml -f version_type=minor # Specific bump type

# Or via GitHub UI: Actions → Release → Run workflow
```

**Alternative: Local Script (for testing)**

```bash
# Auto-detect version from commits and push
bun run scripts/create-release.ts --push

# Specify exact version
bun run scripts/create-release.ts --version 1.2.3 --push
```

That's it! The workflow will:

1. ✅ Update the version files (see [Version Files](#version-files)) and regenerate `CHANGELOG.md`
2. ✅ Commit the changes
3. ✅ Create and push git tag `v1.2.3`, plus a draft GitHub release carrying the changelog
4. ✅ Build Desktop, iOS, Android and the CLI simultaneously
   - iOS updates `project.yml` during build
   - Android calculates `versionCode` during build
5. ✅ Attach all artifacts to the GitHub release
6. ✅ Upload iOS build to TestFlight
7. ✅ Upload Android build to Play Store (Internal)
8. ✅ Publish the release (the desktop workflow's `publish` job flips the shared draft to public)

## Version Management

### Version Files

Our project has multiple version files with different update strategies:

| File                                         | Update Method              | Purpose                                           |
| -------------------------------------------- | -------------------------- | ------------------------------------------------- |
| `package.json`                               | **release.yml** 🤖         | Frontend/Node version                             |
| `cli/package.json`                           | **release.yml** 🤖         | CLI version (what `thunderbolt --version` prints) |
| `src-tauri/Cargo.toml`                       | **release.yml** 🤖         | Rust backend version                              |
| `src-tauri/Cargo.lock`                       | **release.yml** 🤖         | Refreshed via `cargo update --workspace`          |
| `src-tauri/tauri.conf.json`                  | **release.yml** 🤖         | Tauri config (source of truth)                    |
| `src-tauri/gen/android/app/tauri.properties` | **release.yml** 🤖         | Android `versionName`                             |
| `CHANGELOG.md`                               | **release.yml** 🤖         | Regenerated by git-cliff (unified releases only)  |
| `src-tauri/gen/apple/project.yml`            | **ios-release.yml** 🍎     | iOS version (set during build, not committed)     |
| `bundle.android.versionCode` (tauri.conf)    | **android-release.yml** 📊 | Android build number (calculated, not committed)  |

**Update Strategy:**

1. **Committed with the version bump** — everything marked 🤖 above is written by `scripts/create-release.ts` (`updateVersionFiles`, `scripts/create-release.ts:289`) and staged by `commitAndTag` (`scripts/create-release.ts:377`). `CHANGELOG.md` joins the commit only when `--platform all`; platform RC releases skip it.
2. **Platform-specific versions, applied at build time and never committed**:
   - **iOS**: `ios-release.yml` rewrites `CFBundleShortVersionString` and `CFBundleVersion` in `project.yml` (`.github/workflows/ios-release.yml:150`). `CFBundleVersion` is the git commit count — it must increase monotonically within a marketing-version train, and a date-shaped nightly integer would permanently block later stable builds.
   - **Android**: `android-release.yml` writes the calculated `versionCode` into `tauri.conf.json` (`.github/workflows/android-release.yml:123`) and then into `tauri.properties` (`.github/workflows/android-release.yml:159`).

**Important:** `tauri.conf.json` is the source of truth. Platform workflows read from it and update their platform-specific files as needed.

Note that `tauri.properties` carries an `AUTOGENERATED FILE. DO NOT EDIT` banner from the Tauri CLI, but the release path does not treat it that way: `versionName` is rewritten by `updateTauriProperties` (`scripts/create-release.ts:272`) and committed, and `versionCode` is rewritten again during the Android build. Don't hand-edit it; do expect it in release diffs.

### Version Philosophy

- Version files always contain the **next** version to be released
- When you tag `v1.2.3`, all files should already contain `1.2.3`
- Tags point to commits with matching version numbers
- This prevents version mismatches and extra commits

### Android versionCode Calculation

`android-release.yml` calculates the `versionCode` at build time (`.github/workflows/android-release.yml:109`):

```bash
COMMIT_COUNT=$(git rev-list --count HEAD)
BASE_OFFSET=2000
VERSION_CODE=$((BASE_OFFSET + COMMIT_COUNT + GITHUB_RUN_NUMBER * 100 + GITHUB_RUN_ATTEMPT))
```

The run number and attempt are in the formula deliberately, and this is the part that is easy to undo by mistake. Play permanently burns any `versionCode` it has accepted, so a code can never be reused — not by a re-dispatch of the release, and not by a "Re-run" of the same workflow. `GITHUB_RUN_NUMBER` increments on a new dispatch but not on a re-run; `GITHUB_RUN_ATTEMPT` increments on every re-run. Combining them covers both cases. A commit-count-only formula is reproducible, which is exactly the wrong property here: it hands Play a code it has already consumed and the upload is rejected. See THU-643.

The base offset keeps generated codes above the values that were set by hand before this scheme existed.

The `versionCode` is written into `tauri.conf.json` and `tauri.properties` during the build and is never committed back to the repository.

## Release Methods

### Method 1: GitHub Actions (Recommended)

Trigger a unified release for all platforms via GitHub Actions:

```bash
# Via GitHub CLI - Release workflow (simplest)
gh workflow run release.yml -f version_type=auto  # Auto-detect (default)
gh workflow run release.yml -f version_type=patch # Patch bump
gh workflow run release.yml -f version_type=minor # Minor bump
gh workflow run release.yml -f version_type=major # Major bump
gh workflow run release.yml -f version=1.2.3      # Explicit version

# Or via GitHub UI:
# 1. Go to Actions tab
# 2. Select "Release" workflow
# 3. Click "Run workflow"
# 4. Choose version type or enter explicit version
```

**What happens:**

1. **Version Bump** (via `version-bump.yml` workflow):
   - Runs in the `thunderbolt_release` GitHub environment, using a GitHub App token so the bump commit can be pushed past branch protection
   - Updates the version files and regenerates `CHANGELOG.md` via `scripts/create-release.ts`
   - Commits changes and creates unified tag `v1.2.3`
   - Pushes to remote
   - Creates the GitHub release as a **draft prerelease** with the changelog

2. **Platform Builds** (runs in parallel):
   - **Desktop**: Builds all platforms (Linux, macOS, Windows)
   - **iOS**: Updates `project.yml`, builds, and uploads to TestFlight
   - **Android**: Calculates `versionCode`, builds, and uploads to Play Store (Internal)
   - **CLI**: Builds the `thunderbolt` binaries and attaches them with a `SHA256SUMS` manifest — only for `platform=all` and nightly runs (see [CLI Releases](#cli-releases))

3. **Final Release**:
   - All builds upload artifacts to the GitHub release
   - `desktop-release.yml`'s `publish` job flips the shared draft to public and clears the prerelease flag (`--prerelease` stays set only for nightlies)

### Method 2: Local Script (Best for Testing)

Use the local TypeScript script to test version bumping before pushing:

```bash
# Dry run first to see what would happen (safe!)
bun run scripts/create-release.ts --dry-run

# Auto-detect from commits (default behavior)
bun run scripts/create-release.ts

# Auto-detect and push immediately
bun run scripts/create-release.ts --push

# Specify exact version
bun run scripts/create-release.ts --version 1.2.3 --push

# Specify bump type
bun run scripts/create-release.ts --type minor --push
```

**Default behavior:**

- If no `--version` or `--type` is specified, defaults to `--type auto` (auto-detection from commits)
- Updates all version files including `tauri.conf.json`
- Commits the changes
- Creates the tag **locally**
- Tells you how to push when ready (unless `--push` flag is used)

**With --push flag:**

- Does everything above
- Pushes commit and tag to remote

The script prints "this will trigger the release workflow", but nothing listens for the tag. Pushing it publishes the version bump and the tag only; you still have to dispatch `release.yml` (or a per-platform workflow) yourself.

**Why local-first is useful:**

- Review the changes before they go remote
- Test the tag locally
- Avoid triggering expensive CI builds until you're ready

### Method 3: Manual Process

If you prefer complete manual control:

```bash
# 1. Set the version to 1.2.3 in each of these files:
#   - package.json
#   - cli/package.json
#   - src-tauri/Cargo.toml            (then refresh src-tauri/Cargo.lock)
#   - src-tauri/tauri.conf.json
#   - src-tauri/gen/android/app/tauri.properties   (tauri.android.versionName)
#   - CHANGELOG.md                    (git-cliff --tag v1.2.3 -o CHANGELOG.md)

# 2. Commit and push
git add package.json cli/package.json src-tauri/Cargo.toml src-tauri/Cargo.lock \
  src-tauri/tauri.conf.json src-tauri/gen/android/app/tauri.properties CHANGELOG.md
git commit -m "chore: bump version to 1.2.3"
git push origin main

# 3. Create and push tag
git tag v1.2.3
git push origin v1.2.3

# 4. Start the builds — the tag alone does nothing
gh workflow run release.yml -f version=1.2.3
```

Missing `cli/package.json` is the easy one to get wrong: the CLI binaries attach to the same `v1.2.3` release, so a stale bump ships a `thunderbolt` that reports the previous version. `src-tauri/gen/apple/project.yml` is not in the list — `ios-release.yml` rewrites it during the build.

## What Happens During a Release

The `release.yml` workflow handles the entire release process:

### Version Bump Job

1. Updates the version files and regenerates `CHANGELOG.md`
2. Commits with a message like "chore: bump version to 1.2.3 for release"
3. Creates tag `v1.2.3`
4. Pushes commit and tag to remote
5. Creates a draft prerelease on GitHub with the changelog as its body

### Platform Builds

Each child workflow checks out the `v{version}` tag, so all of them build the same commit:

- **Desktop**:
  - **Linux**: `.deb`, `.AppImage`, `.rpm`
  - **macOS (Apple Silicon)**: `.dmg`, `.app.tar.gz`
  - **macOS (Intel)**: `.dmg`, `.app.tar.gz`
  - **Windows (x64)**: `.msi`, `.exe`
  - **Windows (ARM64)**: `.msi`, `.exe`
- **iOS**: `.ipa` uploaded to TestFlight
- **Android**: `.aab` uploaded to Play Store (Internal Track)
- **CLI**: `thunderbolt-cli-{darwin-arm64,linux-x64,linux-arm64}` plus `SHA256SUMS`

Desktop builds are `fail-fast: false`, and the `publish` job runs on `!cancelled() && needs.draft.result == 'success'` — a single failed platform does not hold back the release, it just ships without that artifact.

### Final Steps

- **GitHub Release**: All artifacts uploaded, then flipped from draft to public by `desktop-release.yml`'s `publish` job
- **CrabNebula Cloud**: The desktop release is published to the auto-updater channel (see [Auto-Updater Distribution](#auto-updater-distribution))
- **iOS TestFlight**: Testers with access are notified
- **Android Play Store**: Available on internal track for testing

## Platform-Specific Releases

`release.yml` takes a `platform` input (`all`, `ios`, `android`, `desktop`) and gates each child job on it, so `gh workflow run release.yml -f platform=ios` is the one-step route: it bumps, tags and builds. Dispatching `version-bump.yml` on its own only bumps and tags — the fan-out lives in `release.yml`, so you then dispatch the platform workflow yourself.

### iOS-Only Releases

To release only iOS to TestFlight without a full release:

```bash
# Bump, tag and build in one step (recommended)
gh workflow run release.yml -f platform=ios -f version_type=auto

# Or bump and tag only
gh workflow run version-bump.yml -f platform=ios -f version_type=auto

# Or build an already-tagged version
gh workflow run ios-release.yml -f version=1.2.3 -f notify_testers=true
```

**Note**: Creates RC tag like `v1.2.3-ios-rc`

### Android-Only Releases

To release only Android to Play Store without a full release:

```bash
# Bump, tag and build in one step (recommended)
gh workflow run release.yml -f platform=android -f version_type=auto

# Or bump and tag only
gh workflow run version-bump.yml -f platform=android -f version_type=auto

# Or build an already-tagged version
gh workflow run android-release.yml -f version=1.2.3 -f notify_testers=true
```

**Note**: Creates RC tag like `v1.2.3-android-rc`

### Desktop-Only Releases

To release only desktop without mobile:

```bash
gh workflow run release.yml -f platform=desktop -f version_type=auto
```

**Note**: Creates RC tag like `v1.2.3-desktop-rc`

RC tags are excluded from the changelog on purpose: `cliff.toml:59` sets `tag_pattern = "v[0-9]+\\.[0-9]+\\.[0-9]+$"`, so `v1.2.3-ios-rc` is not treated as a release boundary and its commits stay pending for the next unified release. `create-release.ts` skips `CHANGELOG.md` entirely for platform releases for the same reason. The CLI also sits out single-platform dispatches — it belongs to the unified tag, not to an RC.

## Nightly Releases

`release.yml` runs on a `schedule` at `0 5 * * *` (05:00 UTC, midnight EST) in addition to `workflow_dispatch`. A nightly always builds all four targets regardless of the `platform` input, because each child job's `if` carries `|| github.event_name == 'schedule'`. The `nightly` flag is threaded down to every child as `nightly: ${{ github.event_name == 'schedule' }}`.

Nightlies differ from dispatched releases in ways worth knowing before you go looking for a missing commit or a missing update:

- **The version is dated and the tag is replaced in place.** `version-bump.yml` builds `{base}-nightly.{YYYYMMDD}` from the current `package.json` version and tags `v{that}`. If today's tag already exists (a re-run, or a manual `schedule`-shaped trigger), it deletes the existing tag and its GitHub release and recreates them.
- **Nothing lands on `main`.** The nightly path commits the version-file edits locally and pushes only the tag. `git-cliff` is not installed, no changelog is generated, and `version-bump.yml` does not create the GitHub release — `desktop-release.yml`'s `draft` job does, titled "Nightly Build v{version}", draft and prerelease, with an instability warning in the body. (`cli-release.yml`'s `ensure-release` job races it and creates a plain draft if it wins, so the CLI matrix always has somewhere to upload; the desktop step then updates that release in place.) The release stays a prerelease after `publish`.
- **The auto-updater never sees a nightly.** All three CrabNebula steps are gated on `!inputs.nightly`.
- **iOS and Android are not gated.** Both still upload to TestFlight and the Play Store internal track on a nightly; the flag only changes a log line for them.

## Auto-Updater Distribution

GitHub Releases carry the downloadable artifacts, but the in-app Tauri updater is served by **CrabNebula Cloud**. `desktop-release.yml` drives it in three steps, all authenticated with `CRABNEBULA_CLOUD_API_KEY`:

1. `release draft thunderbird/thunderbolt {version}` in the `draft` job
2. `release upload … --framework tauri` after each matrix build
3. `release publish … --framework tauri` in the `publish` job

The upload step is `continue-on-error: true`, and that is deliberate. A matrix leg that finishes late (macOS Apple Silicon queued behind the other runners, typically) can reach CrabNebula after the release has flipped to published, and `cn release upload` then fails with "release was already published". The tolerated outcome is that the GitHub Release still has the asset while the auto-updater for that one platform misses that one version. The workflow emits a `::warning title=CrabNebula upload failed::` annotation so the case stays visible instead of passing silently — check the run's annotations after every release, and re-upload manually if one fired. See THU-643.

For exercising updates without a real release, see [docs/internals/dev-tooling/local-cdn-for-app-update-testing.md](docs/internals/dev-tooling/local-cdn-for-app-update-testing.md).

## CLI Releases

`cli-release.yml` builds the standalone `thunderbolt` CLI and attaches the binaries plus a `SHA256SUMS` manifest to the shared `v{version}` release. The desktop app's "Install CLI" flow derives its download URLs from its own version (`src-tauri/src/cli_installer.rs`):

```text
https://github.com/thunderbird/thunderbolt/releases/download/v{version}/thunderbolt-cli-{target}
https://github.com/thunderbird/thunderbolt/releases/download/v{version}/SHA256SUMS
```

That URL contract is why the job only runs for `platform=all` and nightlies: single-platform dispatches produce RC tags the CLI does not belong to. A release that predates this pipeline has no such assets, and the installer surfaces that honestly as `CliInstallError::NotPublished` rather than falling back silently.

Three points about the build that are easy to break:

- **The matrix uses native runners, never cross-compilation.** The CLI depends on `@number0/iroh`, a NAPI addon shipping per-platform prebuilt `.node` files, and `bun build --compile` embeds only the `.node` present on the build machine. Each target must build on a runner of its own architecture.
- **There is no `darwin-x64` binary.** iroh publishes no `x86_64-apple-darwin` addon, so an Intel-macOS CLI cannot load it. Intel Mac users have no one-click CLI install until that changes upstream.
- **Publishing is atomic, and is not this workflow's job.** Each leg uploads a workflow artifact; a separate `publish` job gated on every leg succeeding downloads them all, generates `SHA256SUMS`, and uploads the set in one go — so a failed leg can never leave a partial set with a mismatched manifest. Flipping the release to public belongs to `desktop-release.yml`; the CLI only ever calls `gh release upload`, which cannot mutate draft state and therefore cannot race that flip.

## Testing Workflow Changes

**Never push workflow changes directly to `main`.** Open a PR and let the `pull_request`-triggered workflows exercise the change: `ci.yml`, `e2e.yml` and `security.yml` all run on PRs against any branch.

The release workflows cannot be reached that way — nothing in the release path listens for `pull_request`. `release.yml` has only `workflow_dispatch` and the nightly `schedule`; the four child workflows are `workflow_dispatch`/`workflow_call` only. To test a change to one of them, push the branch to `origin` and dispatch against that ref:

```bash
git push origin my-workflow-change
gh workflow run release.yml --ref my-workflow-change
```

A dispatch against a non-default ref runs that ref's copy of the workflow, so this is a real test — but it is also a real release: `version-bump.yml` commits, tags and pushes to the branch you dispatched from. When you only need to prove a desktop platform still builds, dispatch `test-build.yml` instead; it builds one platform and uploads the bundle as a workflow artifact, with no tagging or release side effects.

## Troubleshooting

### Version Mismatch

Nothing in the pipeline validates that the version files agree with the tag, so a mismatch does not fail fast — it ships. The symptoms are downstream: an app reporting the wrong version, or a `thunderbolt` CLI whose `--version` lags the release it was attached to because `cli/package.json` was missed.

What does fail visibly is a missing tag. Every child workflow checks out `ref: v{version}`, so dispatching a platform workflow for a version that was never tagged fails at checkout.

**Solution:** re-run `scripts/create-release.ts` with an explicit `--version` on a clean tree so every file moves together. The older `create-version-tag.yml` helper still exists but bumps only `package.json`, `Cargo.toml`, `tauri.conf.json` and `gen/apple/project.yml` — it predates the CLI and the changelog, and its success message about triggering a release is no longer true.

### Build Failures

1. **Check GitHub Actions logs** for detailed error messages
2. **Check the run's annotations** — a failed CrabNebula upload is a warning, not a failure
3. **Verify secrets are configured** (especially for iOS/Android signing)
4. **Test the workflow** from a pushed branch before merging (see [Testing Workflow Changes](#testing-workflow-changes))
5. **Check recent changes** that might have broken the build

### iOS Build Issues

Common issues:

- **Signing certificates expired**: Update secrets in GitHub repository settings
- **Provisioning profile issues**: Regenerate and update `APP_STORE_PROVISIONING_PROFILE` secret
- **Xcode version**: Workflow uses Xcode 26.2 (iOS 26 SDK)

### Re-running One Platform

Each child workflow is independently dispatchable against an existing tag, which is how you recover a platform that failed after the release went out:

```bash
gh workflow run desktop-release.yml -f version=1.2.3
gh workflow run ios-release.yml -f version=1.2.3
gh workflow run android-release.yml -f version=1.2.3
gh workflow run cli-release.yml -f version=1.2.3
```

`version` is required on all four — they check out `v{version}` rather than the dispatched ref's HEAD.

## Required GitHub Secrets

The following secrets must be configured in your repository. `version-bump.yml` and the desktop, iOS and Android build jobs all run in the `thunderbolt_release` GitHub environment, so environment-scoped secrets and any approval rules on that environment apply to them. `cli-release.yml` and `desktop-release.yml`'s `draft` and `publish` jobs do not, so anything they read must be a repository-level secret.

### Release orchestration

- `RELEASE_APP_CLIENT_ID` - GitHub App client ID used by `actions/create-github-app-token`
- `RELEASE_APP_PRIVATE_KEY` - GitHub App private key. The resulting token is what checks out and pushes the bump commit and tag, so it must be able to push past branch protection on `main`.

`git-cliff` is a hard prerequisite of a non-nightly bump; `version-bump.yml` installs it on the runner, and `scripts/create-release.ts` fails loudly if it is missing when run locally.

### Desktop (all platforms)

- `TAURI_SIGNING_PRIVATE_KEY` - Tauri updater signing key
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` - Password for signing key
- `CRABNEBULA_CLOUD_API_KEY` - CrabNebula Cloud; feeds the in-app auto-updater (see [Auto-Updater Distribution](#auto-updater-distribution))

### Desktop (macOS code signing and notarization)

The macOS DMG is signed and notarized with Apple credentials in addition to being Tauri-signed. Several of these share names with the iOS list below and are the same secrets.

- `APPLE_DEVELOPER_CERTIFICATE` - Apple Developer signing certificate (base64-encoded `.p12`)
- `APPLE_DEVELOPER_CERTIFICATE_PASSWORD` - Certificate password
- `APPLE_SIGNING_IDENTITY` - Signing identity (the workflow also auto-detects it from the imported certificate)
- `APP_STORE_CONNECT_API_KEY` - App Store Connect API key, used for notarization
- `APP_STORE_CONNECT_API_KEY_ID` - API key ID
- `APP_STORE_CONNECT_ISSUER_ID` - API issuer ID
- `APPLE_TEAM_ID` - Apple Developer Team ID

### iOS

- `APPLE_CERTIFICATE_P12` - Apple distribution certificate (base64 encoded)
- `APPLE_CERTIFICATE_PASSWORD` - Certificate password
- `APP_STORE_PROVISIONING_PROFILE` - Provisioning profile (base64 encoded)
- `APP_STORE_CONNECT_API_KEY` - App Store Connect API key (base64 or raw .p8)
- `APP_STORE_CONNECT_API_KEY_ID` - API key ID
- `APP_STORE_CONNECT_ISSUER_ID` - API issuer ID
- `APPLE_TEAM_ID` - Apple Developer Team ID

### Android

- `ANDROID_UPLOAD_KEY` - Upload keystore (base64 encoded)
- `ANDROID_UPLOAD_KEY_ALIAS` - Keystore alias
- `ANDROID_UPLOAD_KEY_PASSWORD` - Keystore and key password
- `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` - Play Console service account used by `.github/actions/upload-to-play`, which uploads the `.aab` for package `net.thunderbird.thunderbolt` to the `internal` track

The signing step hard-fails if any of the three keystore secrets is empty rather than producing an unsigned build. Note that `ANDROID_KEY_ALIAS` and `ANDROID_KEY_PASSWORD` appear in the workflow as `$GITHUB_ENV` variables derived from the `ANDROID_UPLOAD_KEY_*` secrets — they are not secrets themselves.

## Environment Variables

Repository variables (not secrets):

- `VITE_THUNDERBOLT_CLOUD_URL` - Backend URL baked into every desktop, mobile and CLI build
- `THUNDERBOLT_APP_URL` - App URL baked into the CLI build; `cli-release.yml` fails the build if either variable is unset

## Best Practices

1. ✅ **Always use the workflow or the script** for version bumps — they update every file for you
2. ✅ **Test workflow changes from a pushed branch** before merging (see [Testing Workflow Changes](#testing-workflow-changes))
3. ✅ **Use semantic versioning** (major.minor.patch)
4. ✅ **Write good commit messages** for auto-detection to work
5. ✅ **Check version files** are in sync before manually tagging
6. ✅ **Check the run's annotations** for a CrabNebula upload warning before calling a release done
7. ❌ **Never force push** to main or version tags
8. ❌ **Don't hand-edit** `gen/android/app/tauri.properties` — the release script and the Android build own it

**TL;DR on version updates:**

- Use the local script (`scripts/create-release.ts`) → everything updates automatically ✅
- Use the GitHub Actions workflow → everything updates automatically ✅
- Manual updates → you must update `package.json`, `cli/package.json`, `src-tauri/Cargo.toml`, `src-tauri/Cargo.lock`, `src-tauri/tauri.conf.json`, `src-tauri/gen/android/app/tauri.properties` and `CHANGELOG.md` ✏️
- Left to the build, never committed → `gen/apple/project.yml` and the Android `versionCode` 🏗️

**Recommended workflow:**

1. Test locally with `--dry-run` flag to see what changes
2. Run the script without `--push` to commit and tag locally
3. Review the changes
4. Push when ready (manually or with `--push` flag)
5. Dispatch `release.yml` to build and publish

## Rollback

If you need to rollback a release:

```bash
# Delete the tag locally and remotely
git tag -d v1.2.3
git push origin :refs/tags/v1.2.3

# Delete the GitHub release (via UI or CLI)
gh release delete v1.2.3

# Revert version changes if already merged
git revert <commit-hash>
git push origin main
```
