# Managed Inference Usage Guardrails Design

## Status

Approved design delta for managed inference token accounting and rolling soft quotas. This document replaces only the GLM usage transport decision. The shared price table, usage ledger, quota policy, and direct model behavior remain unchanged.

## Goals and trust boundary

The backend owns the authenticated user, canonical provider and model, price snapshot, cost calculation, quota decision, and ledger insertion for all managed models.

For DeepSeek and Opus, the backend also owns token quantities because it observes upstream usage. For GLM, the official frontend reports token quantities after SecureClient decrypts each completed model step. A modified client can omit or forge those quantities. GLM accounting is accidental-cost control, not adversarial enforcement. This limitation is accepted for the MVP.

The encrypted GLM request body remains opaque. The backend treats an exact authenticated proxy POST whose resolved upstream pathname is `/v1/chat/completions` as canonical `tinfoil/glm-5-2`. It cannot verify the encrypted model value.

## Managed models and prices

Rates are nanoUSD per token:

| Public model        | Canonical provider | Canonical model     | Input | Output |
| ------------------- | ------------------ | ------------------- | ----: | -----: |
| `deepseek-v4-flash` | `tinfoil`          | `deepseek-v4-flash` |   300 |    700 |
| `opus-5`            | `anthropic`        | `claude-opus-5`     | 5,000 | 25,000 |
| `glm-5-2`           | `tinfoil`          | `glm-5-2`           | 1,500 |  5,250 |

These values are the approved baseline, not a substitute for a release-time check. Reverify all three against official provider sources immediately before creating the seed migration. Record the verification date beside the seed and the independent integration oracle. If an exact rate differs, update both places. Stop only when an exact canonical SKU price cannot be established.

## Data model

`backend/src/db/inference-usage-schema.ts` defines both server-only tables. `inference_prices` has `provider` and `model` as a composite primary key, nonnegative Drizzle bigint `{ mode: 'bigint' }` input and output rates, and a database-clock `updated_at` timestamp.

`inference_usage` is server-only and has:

- Text primary key `id`, generated by server-side `crypto.randomUUID()` and validated as a canonical UUID.
- `user_id` referencing `user.id` with cascade deletion.
- Canonical text `provider` and `model`.
- Nonnegative PostgreSQL integer `prompt_tokens`, `completion_tokens`, and `total_tokens`.
- Nonnegative Drizzle bigint `{ mode: 'bigint' }` `cost_nano_usd`.
- Database-clock `created_at` timestamp.
- Index `(user_id, created_at)`.

There is no foreign key from usage to prices. Neither table is added to PowerSync or a frontend schema.

Cost is calculated with bigint arithmetic:

```text
costNanoUsd = promptTokens * inputNanoUsdPerToken
            + completionTokens * outputNanoUsdPerToken
```

The implementation rejects values above PostgreSQL bigint maximum. Cached and reasoning tokens do not receive separate pricing.

Stream and receipt parsers continue to accept nonnegative JavaScript safe integers. The persistence boundary defines `maxPostgresInteger = 2_147_483_647` and rejects any larger token count before insertion. On a direct stream this is an isolated usage-consumer failure, so inference still completes without a row. The receipt endpoint maps the same persistence input error to body-free `400`.

## Rolling quotas

Quota settings are integer cents:

| User class | Five hours | Seven days |
| ---------- | ---------: | ---------: |
| Anonymous  |         10 |         60 |
| Registered |      1,500 |      7,500 |

The environment-backed settings and defaults are:

- `INFERENCE_QUOTA_ANONYMOUS_5H_CENTS=10`
- `INFERENCE_QUOTA_ANONYMOUS_7D_CENTS=60`
- `INFERENCE_QUOTA_REGISTERED_5H_CENTS=1500`
- `INFERENCE_QUOTA_REGISTERED_7D_CENTS=7500`

All four settings require positive integers. Add them to `backend/.env.example`. Change deployment configuration only after inspecting whether a deployment needs explicit overrides instead of defaults.

Before every managed upstream call, the backend loads the canonical price and reads both rolling totals with one aggregate query. The query uses the database clock and completed usage only. There are no reservations, locks, counters, or Redis.

A request is allowed only while both prior totals are strictly below their limits. Reaching or exceeding either limit rejects the next request. A completed request may still overshoot because there is no reservation.

Missing price returns a minimal `503` body with `INFERENCE_PRICE_UNAVAILABLE`. Exceeded quota returns a minimal `429` body with `INFERENCE_QUOTA_EXCEEDED` and one exceeded window. The five-hour window wins when both are exceeded:

```json
{ "error": { "code": "INFERENCE_PRICE_UNAVAILABLE" } }
```

```json
{
  "error": {
    "code": "INFERENCE_QUOTA_EXCEEDED",
    "window": "5h"
  }
}
```

## Direct model accounting

DeepSeek and Opus declare `supportsStreamUsage: true`, which forces `stream_options: { include_usage: true }` server-side. The backend ignores client control of that policy. Explicit opt-in prevents a newly added provider from silently being assumed to support stream usage, so this capability is not fake configurability.

The SSE adapter forwards upstream chunks in order without mutating them. It remembers the latest usage object whose prompt, completion, and total counts are nonnegative safe integers. Total need not equal prompt plus completion.

After natural upstream exhaustion, the adapter awaits one usage consumer before emitting synthetic `[DONE]`. The consumer inserts one row with canonical user, provider, model, and request-start rates. Consumer failure is caught and logged without content, then `[DONE]` is emitted.

Lifecycle rules are exact:

- Upstream error: no consumer call and no row.
- Provider-chunk enqueue failure before natural exhaustion: no consumer call and no row.
- Cancellation before natural exhaustion: abort upstream, ignore a previously seen snapshot, and omit `[DONE]`.
- Natural exhaustion without valid usage: emit missing telemetry and `[DONE]`, with no row.
- Synthetic `[DONE]` enqueue failure after natural exhaustion: the ledger attempt has already happened and is not rolled back.
- Cancellation during the awaited consumer after natural exhaustion: let the consumer settle, do not abort it, and omit `[DONE]` for the cancelled downstream.
- SDK retries before a successful stream still produce at most one row for the logical response.

Usage may appear on intermediate or final chunks without `choices: []`. A malformed later snapshot does not erase an earlier valid snapshot. The observer retains only copied numeric counts, never a provider-owned chunk or usage object.

When PostHog wrapping is enabled, `posthogDistinctId` is the authenticated user ID, usage remains present, and content remains excluded.

## GLM signed receipt

### Proxy issuance

The system Tinfoil provider sets `includeUsage: true`; the OpenAI-compatible provider serializes encrypted `stream_options.include_usage`. The proxy does not read or rewrite the body.

For the exact managed GLM chat POST, the proxy performs price and quota checks before upstream, then creates a unique event ID with `crypto.randomUUID()` and a signed receipt using request-start rates. It forwards request and response bytes unchanged.

Only an exact successful 2xx managed GLM chat response receives `X-Inference-Usage-Receipt`. The header is absent for near misses, other methods, non-chat paths, and errors. It is added to the existing CORS expose list. SecureClient preserves it and AI SDK exposes lower-case `x-inference-usage-receipt` in `step.response.headers`. No preflight receipt endpoint is needed.

`shared/inference-usage.ts` is the single mandatory owner of the receipt header name, relative endpoint path, and request body type. Backend and frontend consumers import it read-only.

### Token format

The token is:

```text
iu1.payload-base64url.signature-base64url
```

The payload is UTF-8 JSON containing strict claims:

```json
{
  "purpose": "inference-usage-receipt",
  "version": 1,
  "eventId": "e8c39457-8831-4c10-86ae-8623b6ce2750",
  "userId": "user-id",
  "provider": "tinfoil",
  "model": "glm-5-2",
  "inputNanoUsdPerToken": "1500",
  "outputNanoUsdPerToken": "5250",
  "issuedAt": 1787616000,
  "expiresAt": 1787623200
}
```

Rates are unsigned canonical decimal strings. Times are integer Unix seconds. Receipts expire exactly two hours after issuance. Verification allows `issuedAt` up to 60 seconds in the future.

Base64url is unpadded. The signing input is the exact raw ASCII `iu1.` prefix followed by the received payload segment. The key and signature are:

```text
receiptKey = HMAC-SHA-256(
  key = BETTER_AUTH_SECRET,
  data = "thunderbolt/inference-usage-receipt/key/v1"
)
signature = HMAC-SHA-256(key = receiptKey, data = signingInput)
```

Domain separation prevents direct key and cross-protocol signature reuse. The trade-off is coupled rotation and compromise: Better Auth secret rotation invalidates outstanding receipts, and root-secret compromise affects both systems. A two-hour lifetime bounds rotation impact without another secret-management surface.

Verification requires exactly three segments and the base64url character set, decodes the segments, derives the domain-separated key, and compares the signature with a timing-safe operation over the raw payload segment. Only then does it parse and strictly validate purpose, version, canonical UUID event ID, provider exactly `tinfoil`, model exactly `glm-5-2`, decimal rates, issue time, two-hour expiry, and future skew. Missing or wrong provider/model claims fail validation. It does not require JSON key order, reserialization equality, or a golden token representation. No unsigned identity or price field is accepted.

The internal verifier returns validated claims or `null`. Focused tests preserve branch-level validation coverage, but the route does not expose malformed/expired reason variants because every invalid receipt has the same body-free `400` contract.

### Receipt endpoint

`POST /v1/inference-usage/receipts` is authenticated. Its body contains only:

```json
{
  "receipt": "iu1.canonicalPayload.canonicalSignature",
  "promptTokens": 16,
  "completionTokens": 2,
  "totalTokens": 18
}
```

Counts must be nonnegative safe integers. Total need not equal prompt plus completion. The endpoint verifies the token, checks the current user, requires the canonical GLM identity, calculates cost from signed rates, and inserts with the signed event ID.

`ON CONFLICT DO NOTHING` makes sequential and concurrent replay return `204` across replicas. This is receipt replay protection, not durable provider exactly-once delivery.

Responses have no body:

- `204` for inserted or duplicate.
- `400` for malformed, invalid, expired, future-issued, noncanonical, out-of-range counts, or cost overflow.
- `403` for a valid receipt owned by another user.
- `503` when persistence is unavailable.

The endpoint does not reload current price. Missing or aborted receipts create no row. Database or callback failure never breaks a completed chat.

### Frontend callback

`onStepFinish` handles every completed upstream step independently. It reads that step's header and aggregate usage, validates all counts, and awaits an authenticated `HttpClient.post('inference-usage/receipts', { json: body })` inside an explicit catch so chat continues on failure. This is not fire-and-forget: the ledger attempt precedes the next automatic tool or model step.

The callback does not use `onFinish.totalUsage`. Tool loops can invoke multiple model steps, each with its own receipt and row. AI SDK `6.0.190` awaits async `onStepFinish` before the next step or final completion.

The callback does nothing for non-system GLM, non-GLM, missing header, invalid or missing usage, and interrupted steps. A real GLM contract probe observed four valid usage objects and latest aggregate `16/2/18`; tests must not assume only one usage object within a step.

## Telemetry and privacy

Emit body-free structured events for issued, completed, inserted or duplicate, missing, and callback-failed outcomes. Allowed fields are event name, provider, model, event ID when known, route, status, and outcome.

Never log prompts, completions, encrypted bytes, receipt tokens, authorization, complete headers, raw error objects, tool arguments, or response bodies. No alert subsystem is added.

## Explicit exclusions

- Bun upgrade.
- `node:https`, response trailers, `TE` or `Connection` injection, and Undici.
- Helper process, sidecar, second container, or manual HTTP parser.
- Request-byte estimates.
- Pending rows, reservations, schedulers, locks, counters, or Redis.
- Non-streaming inference.
- Frontend or PowerSync copies of the inference tables.

## Acceptance criteria

- Drizzle generates both tables, a sanctioned custom price seed, and valid journal and snapshot metadata.
- The seed uses three explicit INSERT statements and records the official verification date beside an independently dated integration oracle.
- Account cascade and anonymous-to-registered promotion preserve the approved usage ownership behavior, and no inference table appears in PowerSync.
- Direct streams record the latest valid usage only after natural exhaustion and preserve all lifecycle rules.
- Exact successful GLM chat responses expose one signed receipt per upstream step without changing opaque bytes.
- The receipt endpoint is authenticated, replay-safe across replicas, snapshot-priced, and body-free.
- The official frontend submits one awaited receipt per completed GLM step and isolates callback failures.
- One database-clock aggregate query enforces both windows before every managed upstream call.
- A deterministic fixture records 10,000,000, 50,000,000, and 41,250,000 nanoUSD, then rejects the fourth anonymous request at 101,250,000 nanoUSD completed five-hour spend.
- Focused, full, repeated, bounded live provider reconciliation, and actual app validation pass without exposing content or secrets. Missing admin credentials, contaminated dedicated keys, or reporting timeout are explicit human blockers, never a passing result.
