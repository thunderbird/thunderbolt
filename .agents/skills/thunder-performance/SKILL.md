---
name: thunder-performance
description: Profile Thunderbolt performance with the production browser harness and prove a fix against a baseline. Use when the app feels slow, laggy or janky; for CPU or memory use, a suspected leak, startup time, long chats or large accounts; to find a performance regression; or to show a change is faster.
---

Use this for Thunderbolt performance investigations and regressions. The harness lives in `scripts/performance/`; its operating guide is `docs/internals/development/performance.md`.

Read repository instructions and preserve unrelated work. When a fresh branch is requested, fetch main and use an isolated worktree. Never compare a production build with Vite development mode.

1. Install the locked root and backend dependencies and the repository's Chrome Stable build. Build the unchanged app with `bun run perf:build -- qa-dist-perf-before`, then serve it with `bun run perf:serve -- qa-dist-perf-before` in a separate terminal.
2. Run `bun run perf -- --label before`. It creates disposable local users, imports deterministic long conversations through the real UI, exercises desktop/mobile interactions at 4× CPU slowdown, and writes raw JSON plus screenshots under `qa-out-performance/`. It requires no provider credentials. Keep other builds, tests, browsers and benchmarks idle during timing runs.
3. Investigate the worst measured interactions. The full suite includes Playwright assertions in its windows, so trace attribution must distinguish driver accessibility work from app work. For focused measurements, serve both builds with `bun run perf:serve -- qa-dist-perf-before qa-dist-perf-after`, then run `bun run perf:paired -- --pairs 3 --profile mobile --journeys typing,stream --label paired`. This alternates before/after order, moves assertions outside timing, and uses a named high-rate markdown fixture. Keep both sides on the same fixture/instrumentation version. Add `--trace --pairs 1` for attribution; tracing perturbs timings. Use the optional markdown benchmark only to attribute parser work, not as a substitute for browser results.
4. Confirm the hot path actually runs in the app before editing. Prefer removing duplicate work, stable callbacks and narrower subscriptions. Before memoizing, check for mutable external reads that currently refresh through parent renders, and test status/model/locale changes. Add regression tests for the behavior being preserved and the work being avoided. Avoid timing assertions in unit tests, broad memoization, caches without bounds, and visual simplifications unsupported by measurements.
5. Build the changed app into a second directory, stop the baseline server, and serve the new build on the same ports. Run the same profiles, CPU rate and repetitions with `--label after`. Use `bun run perf:compare -- qa-out-performance/before.json qa-out-performance/after.json`. Inspect regressions as well as improvements; rerun noisy comparisons without changing scenarios between builds.
6. Run the scoped tests and type/lint/format checks appropriate to all changed files, including `bun run test:performance`. Check phone screenshots, keyboard focus, scrolling, streaming cancellation and completed-message persistence when affected.

For initial-load work, use `bun run perf:startup -- --runs 3 --profile mobile --label startup-before`. It measures first usable input on a fresh signed-out profile, performs real sign-in/import outside timing, restarts Chrome with the retained local database, and measures the returning composer. Keep the build frozen while collecting baseline samples; match route/cache policy on the candidate. `--chat long` adds restored long-chat hydration; `--trace --runs 1` captures startup screenshots and parser/compiler attribution. Inspect resource compression, actual network/cache status, existing boot marks and the separate post-ready CPU window before attributing a delay. Do not interpret loopback transfers as production-network timing or compare startup samples through the full-suite comparator.

For large accounts or long-session retention, use `bun run perf:large-session -- --label large-before`, then repeat against the candidate with identical fixture/cycle options. It warms all sampled chats before repeated navigation blocks and snapshots the same checkpoint route; distinguish retained sessions and query caches from continuing growth. This runner supports Chromium only. WebKit mode was removed because the installed macOS WebKit 27.2 shares OPFS between fresh persistent profiles; earlier WebKit reports do not establish isolated fixture or performance evidence. Do not delete shared storage to bypass this limitation; see the guide. `bun run perf:search-index` isolates FTS write amplification and rebuild cost in native SQLite; do not present its timings as browser latency.

Report measured changes, test evidence and remaining bottlenecks. Link the local raw reports and Chrome traces. Separate Playwright action time from browser Event Timing; rAF gaps are main-thread scheduling evidence, not GPU frame-rate measurements. Heap snapshots and one positive retention delta do not prove a leak. CPU throttling and a mobile viewport are a repeatable proxy, not a physical low-end phone; desktop-hosted WebKit does not reproduce a phone's GPU or software keyboard.

The harness changes only disposable local test accounts. Never point it at a user's live account or add benchmark hooks to the production app. Keep reports/builds gitignored; retain a concise findings document when useful. Publishing, committing and pushing still follow the user's request and `/thunderpush` convention.
